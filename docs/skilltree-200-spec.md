# Castle Field — クラシック大規模スキルツリー実装仕様書 v1.0

**Claude工場長への実装指示 / 200取得ノード・19系統**

対象リポジトリ: https://github.com/keisuke11163-afk/game

この文書だけで実装に着手できるよう、これまでの構想を具体化した。計画や提案で終わらず実装すること。新規ノードの名称・初期数値・接続配置・12pt・安全上限は、従来の合意を具体化するために補った暫定設計値であり、対戦バランス検証済みではない。明示した仕様と実装済み機能を区別すること。

## 1. 目的・変更範囲

- クラシックに200取得ノード（通常133、奥義19、横断48）を導入する。無料のSTARTはノード数に含めない。19の独立した一本道ではなく、隣接経路を自由に横断する単一グラフを作る。
- 数値強化だけでなく会心、追加発動、属性反応、確率操作、手札操作、死亡・蘇生、兵器、時間、召喚、HP消費などの戦い方の変化を重視する。
- 取得自体に恒久的デメリットを課さない。血魔術等の任意支払は使用時に明示して本人が選択する。選ばなければ従来どおりプレイできる。
- 通常モード（kingdom）・4陣営モード等、クラシック以外の戦闘・乱数順序・カード性能・UI・保存を変更しない。火水風土の追加、カード全体の改修、デッキ方式の変更は今回の対象外。通常・クラシックは既存の共有山札を維持する。
- 以前の24ノード版は未適用・未pushと報告されている。着手時に実際のブランチ・commit・作業ツリーを確認し、classic.tar.gzが利用できるなら内容と競合を調べる。存在しないものを適用済みとみなさない。旧版を重複して適用しない。
- 以前の城性能差をクラシックでスキル側に集約する方針を採用する（外観は残す）。既存の城の固有能力・初期補正をクラシックだけ無効にし、無取得の城基準値は旧クラシックの標準城を採用する。標準城が一意でない場合は現行データと採用値を記録。通常等の城は変更しない。旧セーブはバージョン付きで移行し、旧ノード選択は新規IDへ明確に対応できなければ振り直し扱いにする。対戦途中の旧保存は無理に変換しない。

## 2. 取得ルール・グラフ定義

| 項目 | 初期仕様 |
|---|---|
| 取得ポイント | 12pt（設定値、QAで7/10/12/15などを比較可能） |
| 取得コスト | 全ノード1pt、STARTのみ0pt |
| 奥義 | 最大1個。強制取得なし |
| 開始位置 | 全員共通START |
| 取得条件 | 未取得、STARTから取得済みノードを通じて接続、残ptあり、個別必須ノードを満たす |
| 横断 | 接続先のどちらか一方を取得すれば横断ノードを取得でき、反対側へ進める。両端取得は不要 |
| 振り直し | 対戦前は無料。対戦中の変更禁止 |
| 解除 | 解除後に全取得ノードのSTARTへの連結・必須条件・奥義制限を検証。不正なら拒否 |
| 保存 | ツリー版、取得順序付きID配列、選択肢、設定予算を保存。対戦開始時に両者を再検証 |

各系統のIDは下記表の英字と2桁番号を連結する。例 C01、M08。すべての系統で共通の内部無向辺を使う。**START–01、01–02、01–03、02–04、03–05、04–05、04–06、05–07、06–08、07–08**。08が奥義。横断ノードX01〜X48は第4章の2端点とそれぞれ無向辺を持つ。表以外の辺は追加しない。個別必須ノードは接続判定とは別に必要。横断ノードは通路だけではなく全て固有効果を持つ。

リング状配置の初期案：会心→魔法→属性→状態異常→時間→魔力→手札→模倣→召喚→墓地→血魔術→回復→防御→闘志→兵士→戦術→兵器・罠→攻城。幸運は中央寄りの専用領域に配置。実際の辺は下記定義を優先し、図上の近さだけで取得を許可しない。交差が多い箇所は縮尺、曲線、選択経路のハイライトで判別できるようにする。

明示的な追加取得条件（AND、未記載はなし）：M08→M02、P08→P02、G06→G02、B07→B06、B08→B01、X04→P02、X18→M02、X22→M02、X40→K02。通常の属性や会心など、他の手段で発動条件を満たせるノードは無理に別ノードを要求しない。未取得の基本機能に依存する効果が休眠する場合、UIに発動条件を表示する。

E04の4択とX25の属性選択はノード内設定であり、取得ノード数は増えない。E04初期値は対消滅、X25初期値は炎（実データの対応する属性IDへ解決）。選択可能リストは実装済みデータを参照し、存在しない効果を新設しない。非対応の選択肢があれば報告しUIで無効にする。QAが選択肢を渡さない時は上記の固定初期値を用い、選択肢の探索はadapter拡張で扱う。

- 本番の戦闘エンジンを唯一のルール実装にする。スキルID、group、名称、説明、cost、奥義フラグ、edges、requires、設定、効果パラメータ、効果ハンドラIDをデータで管理し、表示と適用を同一データから生成する。UIで別のルールを実装しない。
- 効果はイベント型共通処理＋小さな効果ハンドラを基本にし、200個の独立した戦闘エンジンを作らない。既存Gameのライフサイクルを調査して適切な拡張点を選ぶ。ブラウザとheadlessで同じ処理を使用。
- プレイヤー単位で取得ID、選択値、発動回数、会心蓄積、幸運蓄積、血気、魂、貯蔵MP、予約効果、残り回数等を管理。プレイヤー間・対戦間で共有しない。状態保存/復元がある場合は全状態を対象とし、相手非公開情報を漏らさない。
- 「各自ターンn回」は自分のターン開始時にリセットし、次の自ターン開始まで（相手ターン中の発動も含む）を1区間とする。開始時効果はリセット後に処理する。試合中n回は試合終了までリセットしない。失敗した確率判定や対象不在では成功回数を消費しない。明記した判定機会の上限は別管理。
- 隣接とは盤面上の縦横1枠（斜めなし）。既存レーン・射程・空き枠・移動制限・攻撃可否を尊重し、スキルで明示した場合だけ例外とする。自動対象は安定したレーン→進軍位置→インスタンスID順で選択。ランダム対象は合法候補の安定ソート後に注入RNGで一様抽選。対象の消滅時は原則不発（明示された再選択は例外）。
- 取得で追加される任意アクションはメイン行動中のみ。既存の手番、リアクション、選択UIに統合する。対象選択、消費、結果プレビュー、キャンセル、CPU/headlessでの合法な選択を用意する。対象・支払い・上限を確定してから原子的に実行し、不成立時には支払いも回数も消費しない。
- 追加ドロー、回収、コピーは既存手札上限と山札枯渇・再補充規則に従う。手札が満杯なら任意取得は拒否、自動追加は不発。選択・探索時に山札全体をクライアントへ公開しない。HP、MP、SP、城壁、シールドの既存上限は維持し、既存上限のない新規城壁・シールド生成には暫定上限10を使用（既存値を削らない）。
- 新規のリソースは魂最大6、貯蔵MP最大5、血気最大8、余剰回復貯蔵最大5。SPとコインはクラシックの実データに従う。闘志は戦闘内SPのみを扱い、アカウント通貨を流用しない。クラシックに対象SPや戦闘コインの仕組みが存在しない場合は現行仕様を確認の上、クラシック専用で必要な最小状態・獲得規則を追加し、既存モードへ波及させない。暫定新設SPは初期0/上限30、非トークン敵兵士の撃破+1。コイン新設時は初期0/魔物撃破+1、上限なしだが生成由来報酬禁止。既存機能があればそちらを優先。

### 5.2 ダメージ・回復・会心

既存の属性相性、防御、城壁、シールド、回復、状態異常、勝敗の順序は維持する。新規処理を挿入する位置は次の通り。実装上既存の順序と相違する場合、既存順序を優先し挿入点を文書化する。

1. 宣言・合法性検査・対象選択・任意支払の確認。原カード/基本効果を確定する。
2. MP/SP/HP等の消費を確定（コスト軽減、置換、免除、延期の順）。使用イベントは実カード使用1回だけ発行。
3. 直接命中ごとに回避→基礎威力補正（固定加算、割合加算）→会心判定/倍率→既存の属性相性・防御・シールド・城壁等のダメージ解決。城壁貫通は城壁処理の直前、軽減・肩代わり・致死防止は城HP減算の直前に適用する。
4. HPの実損失・実回復・余剰・城壁吸収・破壊・死亡・勝敗を既存規則に沿って確定する。属性付着/反応は既存挙動を優先する。
5. イベントキューに発動可能な追加効果を登録し、処理上限の範囲で順に解決する。試合終了確定後は追加効果を破棄する。

会心の初期値は解放前0%。C01取得で兵士通常攻撃と敵兵士への攻撃魔法の直接命中15%/1.5倍。追加攻撃・追加魔法は個別の会心判定を行えるが、5.5の制限に従う。複数対象は対象ごとに1判定。城会心はX10、持続ダメージ会心はX17でのみ解放。反射、固定追撃、罠、属性反応、回復、自己HP支払は原則会心不可。C02/C03等の補正は解放済みの該当カテゴリに適用する。会心確率の通常上限80%（確定会心は別扱い）、倍率上限3.0。豪運倍率は倍率加算後に適用。既存の整数ダメージ丸めを優先し、追加効果の50%威力等は切り捨て、正の元ダメージに対する直接追加攻撃の最小値1。回避した場合は命中/会心/実ダメージ効果を発行しない。

回復は実回復量（上限までに回復した量）と余剰量を別記録。余剰はX08の城壁変換→R02の貯蔵の順に割り当て、同じ回復分を重複利用しない。吸血・反射などの割合由来の固定量は対象ごとに切り捨て（例：吸血10%で9ダメージなら0）、正の整数化を強制しない。発動上限は実際に得た量で加算。最大HP増加は現在HPを自動増加させない。

### 5.3 幸運と乱数

- Math.random等の直接使用禁止。既存Gameの注入RNGを利用し、対象選択と全確率判定を記録。通常モードでは新規乱数を引かない。
- 幸運対象は自分の戦闘内スキルの明示的確率（会心、回避、やまびこ、模倣、召喚、再装填等）。ガチャ、報酬、山札の順序、属性のランダム選択、サイコロ出目そのもの、幸運補正用の内部判定は対象外。敵側の判定には干渉しない。
- 順序：基礎確率＋加算ポイント（会心蓄積・運命蓄積等）→L01の1.1倍→上限（会心80%、その他95%）→L08による最大2回の独立判定→全失敗ならL02の10%判定と成功時の元確率1回再抽選→最終成否。確定会心などの確定効果は確率補正・蓄積を発動しない。最終成否1回につきL03を1回更新。内部乱数は追加の幸運判定を生まない。
- L06は結果が比較可能かどうかにかかわらず本人が選択。CPUは既存評価関数で選び、未対応の場合は決定論的フォールバックとする。二つの結果を同時適用しない。
- X24の翌ターン再試行は元の最終判定の再試行1回だけ。対象・資源・回数・元カードの存在等を再検査し、無効なら破棄する。延期した確率判定からさらに延期を作らない。宣言時限定（支払免除、回避等）の判定は遅延再試行の対象外。

### 5.4 属性・状態異常・時間・召喚・墓地

- 属性は現在のクラシック実装（対消滅、黒氷、砕氷、混沌反応等）と同じ反応表を参照する。二重付着は同時属性を新設せず、既存付着処理を順番に2回使う。E07は既存の反応で消費した付着を1回分だけ復元し、その復元自体では即反応させない。反応ダメージのコピーは付着や新規反応を起こさない。属性拡散・元素暴走は明記された場合のみ追加付着し、既存の合法な反応を1回誘発できる。
- 状態異常は既存の付与、スタック、解除、持続モデルを使用する。毒・出血・やけどのうち未実装のものに限りクラシック専用で「対象のターン開始時に固定1ダメージ、指定期間、同種再付与は期限の大きい方で更新・同一付与元は加算しない」という最小定義を用意。既存定義を置き換えない。付与元を保存し、疫病の即時精算では将来の基礎tickを計算して状態を消費し、通常tickを個別発行しない。
- 予約効果は所有者、対象ID、元イベント、元基礎威力、期限を保存。自ターン開始時に既存の基本更新・リセットの後、HP債務→予約効果→その他のスキル開始時効果の順（既存必須フェーズを動かさない）。予約魔法は元カードを消費しない。元威力は元の手札使用時の基礎値を基準とし、同じ基礎加算を二重適用しない。追加会心は許可範囲で新規判定。
- 兵士/墓地はカードIDと盤面インスタンスIDを区別する。蘇生には既存の墓地・蘇生APIを使用し、成功時に墓地から取り除く。空き枠は既存蘇生規則に従い、なければ不発。HPは最大HPの50%（切り捨て、最低1）、旧状態異常・予約バフは持ち越さない。同一死亡イベントで蘇生と手札回収の両方を成立させない。自動蘇生は各インスタンスにつき試合中1回、手動蘇生も含め1インスタンスの蘇生合計最大2回。新インスタンスにも元の履歴IDを継承。生贄は敵撃破報酬を発行せず、蘇生・召喚・死亡誘発の対象外。
- 弱体トークンは元兵士の基礎最大HPと攻撃力の50%（最低1）、元の基本移動/射程、固有能力なし。使い魔は暫定HP2・攻撃1・移動1・射程1のクラシック専用兵士。自分の通常出撃領域の合法な空き枠へ生成し、既存盤面上限を守る。既存の出撃回数とは別の生成処理だがトークン同時存在上限3体/プレイヤー、生成は各自ターン合計2体まで（試合開始時0）。通常の戦闘対象になるが、墓地に入らず、通常の撃破コイン/SP報酬・死亡時生成・魂・カード回収・再召喚を発生させない。トークン消滅専用イベントは許可する。V08/X06の安全リストは既存の単純な攻撃・射程・防御補正などに限定し、コピー、召喚、蘇生、追加発動、資源獲得は継承不可。選択可能な能力がない場合はV08の元兵士付きトークンにも攻撃力+1を代替適用する。
- コピーカードには元IDとコピー由来を記録し、使ったら消滅させる（手札上での通常使用とMP消費は行う）。山札、墓地、捨て札への恒久追加禁止。コピーからコピーを生成しない。模倣由来カードは通常のカード効果を使用できるが、やまびこはX22がある場合のみ、その他の追加カード生成・コピー・返却効果は無効。模倣を受けた側の手札情報は公開しない。

### 5.5 追加発動・連鎖・イベント順序

- すべての効果イベントに eventId、rootActionId、parentEventId、ownerId、sourceSkillId（あれば）、sourceCardId、targetId、origin、depth、実量、成功/失敗理由を持たせる。originは最低でも hand、normalAttack、echo、chain、reaction、dot、reflect、resurrection、token、copy、scheduled、sacrifice、hpCost、skillActive を識別。必要なら細分化する。
- 同じ原アクション内ではFIFOで追加効果を処理する。同一イベントの複数ハンドラは「状態の確定→致死防止→既存死亡/勝敗→資源・ドロー→追加攻撃・予約」等のイベント段階に分け、同一段階では安定ID順。勝敗確定後は新規効果を処理しない。致死回避はX14→D08→既存の勝敗処理（既存のより優先されるルールがあれば尊重）。
- 追加発動は原則、追加発動を生まない。やまびこはM08の明示的な幾何連鎖だけ例外（追加3回まで）。M02・X01・X27など別の追加発動が同時成立しても、同じ原魔法の追加詠唱は合計3回以下、M08未取得では合計2回以下。追加詠唱を再度「カードを使用した」と扱わない。手札使用時に払ったMP/HPは二重に消費・還元しない。M02に由来する成功時だけX12を判定し、同じ実カードをM05とX12で2回回収しない。
- 追加魔法や追加通常攻撃にも合法な会心と属性反応を認めるが、追加由来の会心からC06/X01/B04等の直接命中時誘発を再起動しない。資源獲得・ドロー・死亡誘発は原則原効果由来のみ。追加のダメージでも既存の死亡処理と勝敗は必ず実行。R06の追加回復では新たな貯蔵・城壁変換・回復誘発を起こさない。反射から反射、蘇生から蘇生、コピーからコピー、召喚から召喚は禁止（X19の1回の追加召喚だけ例外）。X18は予約→やまびこ1回のみ、予約由来から新予約は不可。属性反応のコピーは新しい反応を作らない。元のカードが本来持つ既存効果は維持する。
- 1原アクションにつき新規スキルの派生深度上限8・派生イベント上限128、1プレイヤー区間あたり新規スキル成功イベント上限128を暫定設定する。制限を超えた新規派生だけ停止し、診断イベントを出す。既存の基礎効果や勝敗判定まで中断しない。上限到達はQAで異常候補として記録し、通常のゲームプレイで頻繁に起きるなら修正が必要。
- 対戦開始時に固定効果の適用順を安定化。CPUと人間で処理ルールを変えない。CPU用の選択ロジックは既存戦略へ委譲し、合法行動が取れない場合のみ deterministic なフォールバック（または任意行動を見送る）を用意する。

### 5.6 血魔術と支払処理

- 自発的なHP消費はダメージではなく独立した支払イベント。城HPから直接減算し、城壁・シールド・軽減・回避・反射・致死防止を通さない。支払で自滅する選択は不可（HP1と未払い債務を確保）。HP不足ならアクションを拒否する。
- B01は不足MPだけ置換、B08は任意のMP部分を1:1で置換しB01を上書きする。B03/X27等の追加支払は別の宣言・費用として扱う。MP軽減→HP置換→X32免除→X35延期→実支払の順。免除された量から血気/SP/城壁/回復強化を生成しない。
- X35の延期分は予約された債務として保存。次自ターン開始に最優先で支払う。敵の攻撃でHPが不足した場合はHP1を残す範囲で支払い、残額は債務として次の自ターンに繰越。債務が残る間、新たな任意HP支払・延期は不可（債務支払は再免除/延期不可）。実際に支払った分だけHP支払イベントを出す。支払い済みの量を重複計上しない。
- HPを消費して得た効果による回復が許されるのは明示された範囲だけ。吸血/回復の上限を守る。自分自身へのダメージ、過剰ダメージ、トークンへのダメージ、城壁吸収量から吸血を得ない。

## 6. UI・CPU・保存

- クラシックの対戦前画面にツリーを追加。ドラッグでパン、ホイール/ピンチでズーム、系統検索、選択中の経路強調、残pt、奥義数、取得可否と理由、効果・条件・回数のツールチップ、全リセットを提供。タッチ/PCに対応。通常モードには追加しない。
- START、通常、奥義、横断、取得済、取得可能、未接続、条件不足を色だけでなく形・明暗で判別可能にする。隣接を示す実線と視覚上の配置を一致させる。E04/X25の選択UI、任意スキルの戦闘中ボタン、血魔術の実費プレビューを用意する。
- 対戦中は取得スキル一覧と発動ログ、魂/血気/貯蔵MP/予約/債務/各回数など取得時だけ必要な状態を表示。相手の非公開カードや選択肢を露出しない。効果音・豪華な演出の制作は後工程。既存操作を壊さない。
- CPUは既存戦闘AIを残し、新規任意アクションの合法手を列挙できるようにする。最低限、HP置換/回復/蘇生/移動/ドロー/召喚/確率選択等を安全な範囲で扱えること。高度な戦略最適化はCodex側の後工程。未対応の戦術・選択は明記し、未検証の勝率を報告しない。

## 7. CodexのQAツールとの連携契約

添付 Castle Field QA v0.1 の README（tools/castle-qa/README.md）を確認した。現時点のツールはスキルadapter未接続で、空ビルドのみ許可する設計。ClaudeはQAツール全体の開発・修正を担当しない。本番ゲーム側から以下の契約に必要な情報を公開し、Codexが薄いadapterで委譲できるようにする。名前やパスの最終決定は実リポジトリに合わせ、引き継ぎ文書に記載する。

| QA adapter export | 必要な本番API/機能 |
|---|---|
| `nodes` | `[{id: string, group: string}, ...]` を本番ノードデータから取得 |
| `canAcquire(picked, id, budget)` | 本番取得判定。取得順、接続、必須ID、奥義、実コストを検査 |
| `validate(picked, budget)` | 本番全体検証。QAの任意契約だが公開推奨 |
| `cost(picked)` | 実支払pt（Ablateに必要） |
| `apply(gameOptions, builds, budget)` | 2人分の取得順ID配列を本番Game初期化に渡すための契約。既存オプションを破壊しない |
| `observe(type, payload)` | 数値化できる発動・ダメージ・資源・確率・派生イベントを本番から提供 |
| `verify(game)` | 本番スキル状態・資源上限・合法性を検査できる公開状態または検査API |

- QAのbuildは取得順序を保持したID配列。空ビルドは `[]`。200個の本番ノードをそのまま使い、QA独自の取得ルールや効果シミュレーターを作らない。
- QA向けの既存Game初期化・seeded RNG・firstPlayer・既存strategies.jsの利用を壊さない。任意選択をDOMに依存させず、行動APIから同じルールで実行できること。通常モードは従来どおりadapterを経由せず、スキル処理/乱数消費ゼロ。
- 発動イベントは skillId、発動回数、確率、結果、実ダメージ、実回復、MP/SP/HP/コイン増減、城壁変化、属性反応、蘇生、召喚、追加発動、連鎖深度、発生元を計測可能にする。既知の未発動（0）と未計測（null/未対応）を区別できるようにする。イベントは実処理に基づき、表示上のダミー値は返さない。
- QA側の実戦接続・性能測定・遺伝的探索・回帰テスト・大量対戦・勝率分析はCodex担当。Claudeは契約と引継ぎを完成させる。QAが追跡しているGameイベントの型に実際に合わせること。選択肢付ビルドを現行QAが表現できない場合、初期値での測定を可能にし、オプション探索は追加課題として記録する。

## 8. 実装順序と担当範囲
