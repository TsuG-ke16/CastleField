# Codex に渡すプロンプト：画面（UI）の修正とデザイン

使い方：下の「ここから」〜「ここまで」を、そのまま Codex に貼る。リポジトリ（`keisuke11163-afk/game`）のブランチ `claude/sharp-brown-pakhoz` を最新にしてから始めさせる。

---

## ここから

あなたは、城攻めカードゲーム「キャッスルフィールド」の**画面（UI）担当**です。ゲーム全体の見た目の修正とデザインを任せます。

### 0. 最初にやること

1. リポジトリの `CLAUDE.md` を**最初から最後まで読む**。これが仕様の正です（特に「チーム開発のルール」「担当の分け方」「ロジックとUIの約束」「画像素材」）
2. `assets/STYLE.md` を読む（絵柄の決まりと、画像生成AIに付ける共通の指示文）
3. 動かして見る：リポジトリのルートで `python3 -m http.server` → `http://localhost:8000/?local=1&cpu=easy&debug=1`（CPU と1人で遊べる。`debug=1` で手札や城HPを変えられる）
4. 作業用ブランチを切る：`feature/ui-<内容>`（例：`feature/ui-card-art`）。**main に直接コミットしない。** PR は1つの機能ごとに分ける

### 1. 触っていい範囲

- **触っていい**：`index.html`、`css/`、`js/ui/`、`js/main.js`、`assets/`
- **触らない**：`js/game/`、`data/`、`tests/`、`server/`（ゲームのルール・数値・自動テストはロジック担当の領域）。必要な変更があれば、コードを直さず、PR の説明文に「相手側で必要な変更」として書く
- `CLAUDE.md` は共有ファイル。変更するときは、PR で相手の承認を必須にする
- UI は**ゲームの状態を直接書き換えない**。必ず Game のメソッド（`playCard` など）を呼ぶ。Game は DOM を一切使わない

### 2. ゲームの概要

- 2人対戦の城攻め。手札から兵士・武器・魔法・防御のカードを出し、相手の城HPを0にしたら勝ち
- 城と城の間に道が3本（`laneCount`）。兵士は出す道を選んで進み、同じ道の上で戦う。真ん中のマスに魔物が出て、倒すとコインがもらえる
- スマホの縦画面が基準。PC のブラウザでも崩れないこと
- ゲームづくりの原則（CLAUDE.md「桜井流」）：1試合は10分前後／最初の1分で面白さが伝わる／演出はタップで飛ばせる／押して何も起きない操作を作らない（出せないカードは理由を出す）／攻撃が当たったら、ヒットストップ・画面の揺れ・大きな数字をセットで入れる／勝った人を派手に褒める

### 3. 今の画面の状態（引き継ぎ）

画像ファイルは**まだ1枚もありません**（`assets/` は空）。今の絵はすべて、コードで描いた**仮の SVG** です。

- カード・兵士・魔物・城の絵：`js/ui/art.js`（SVG を文字列で返す。カード種類のキーごとに `CARD_ART`）
- 属性・状態異常・魔物のアイコンと色：`js/ui/look.js`
- 画面の文章（カードの説明文など）：`js/ui/text.js`
- 演出：`js/ui/Animations.js`（Game のイベントを1つずつ演出する）。数値は `js/ui/config.js`
- 盤面の描画：`js/ui/Renderer.js`、手札：`js/ui/HandView.js`
- Game と UI のつなぎ：`js/main.js`

#### 直してほしいこと（まず全体を見て、優先順位を決めてください）

1. **仮の絵を、本番の絵にする**（下の「4. 素材のリスト」）。絵柄は `assets/STYLE.md` に従う
2. **全体のデザインの見直し**：レイアウト、色、文字の大きさ・読みやすさ、ボタン、タイトル画面、手札の見た目。スマホの縦画面で、親指で押しやすく、文字が読めること
3. **演出の見直し**：長すぎる待ち時間がないか、タップで飛ばせるか（`skip()`）、攻撃の手応え（ヒットストップ・揺れ・大きな数字）、勝敗画面の派手さ
4. 最近足した次の演出は、**撮影すると帯が見えないことがあった**（カードの拡大演出と重なる）。タイミングを見直す：「身代わり！」「反射！」の帯（`Animations.js` の `soldierDecoyed` / `spellReflected`）
5. 新しい仕組みの見た目の磨き込み：精霊のバッジ（城のそばの「💧 あと4」、`Renderer.js` の `setSpirit`、`css/style.css` の `.castle-spirit`）、手札が5枚まで補充されることが分かる表示

### 4. 素材のリスト（専用の絵が要るもの）

カードの絵のキーは `data/cards.json` のキー。ファイル名の決まりは `CLAUDE.md`「画像素材」に従う（`cards/card-<キー>.png` など）。

- **カードの絵（512×512）**：既存のカード（歩兵・騎士・槍兵・重装兵・巨人・ファイアボール・隕石・サンダー・大雷・ヒール・小回復・毒の霧・毒の雨・猛毒・氷の息・氷河・大氷結・炎の剣・水の槍・風の弓・土の槌・鉄の剣・盾・大盾・城壁・土嚢）と、新しいカード：
  - 反射（`reflect`）・身代わり（`decoy`）・天の恵み（`blessing`）・神頼み（`prayer`）・盗賊（`thief`）・雷光（`bolt`）
  - 精霊8種：火・水・風・土の「精霊」と「大精霊」（`fireSpirit` / `greatFireSpirit` / `waterSpirit` / `greatWaterSpirit` / `windSpirit` / `greatWindSpirit` / `earthSpirit` / `greatEarthSpirit`）。大精霊は、精霊より立派で光の輪がつく見た目にする
- **カードの枠（512×768）**：`frame-soldier.png`、`frame-spell.png` ほか、種類（兵士・魔法・武器・防御）で色や形を変える
- **兵士（盤面、256×256、青とオレンジの2色）**、**城（横512px、壊れ具合つき）**、**魔物**、**背景（1080×1920）**、**演出（爆発・雷・回復・毒・氷など）**、**ボタン・看板・帯などの画面部品**
- **属性のアイコン**：火・水・風・土の4つ。戦いの強弱は「水→火→風→土→水」の輪（水は火に強い、火は風に強い、風は土に強い、土は水に強い）。見ただけで強弱が分かるデザインにする

### 5. 画像を作るときの決まり（必ず守る）

- 新しい絵は、必ず `assets/STYLE.md` の「共通の指示文」を使って作る。作者や絵柄がばらばらの素材を混ぜない
- 形式：背景が透明な PNG。1枚300KB以下に圧縮する。ファイル名は小文字の英字とハイフンだけ
- プレイヤーの色：p1 は空色（blue）、p2 は夕焼けオレンジ（orange）
- **どのカードにどの画像を使うかは `js/ui/` に書く**（`data/cards.json` には画像の情報を入れない）
- 素材を足すときは、同じPRで `assets/CREDITS.md` に「ファイル名・作った道具（画像生成AIの名前）・ライセンス・作った日」を書く
- 利用規約を確認する。再配布が禁止されている素材は入れない（リポジトリは公開される可能性がある）
- 画像を読めないときも壊れないようにする（今の SVG の絵を、画像が読めないときの代わりに残してよい）

### 6. ロジックとの約束（変えない）

- Game が出すイベント（`CLAUDE.md` の「Gameが出すイベント」の表）を受けて演出する。イベントや `getState()` の形を変えたくなったら、変えずに PR の説明文に書く
- 画面は、イベントで演出し、`getState()` で答え合わせをする（`js/ui/syncCheck.js`、デバッグ時にずれを `console.warn('[sync]')` に出す）
- 出せないカードは、`canPlayCard` の `reason` をそのまま画面に出す
- 表示名など、人が入れた文字列は `textContent` で出す（HTML として入れない）

### 7. 確かめること（PR を出す前に）

- `node --test` が全部通る（ロジックを変えていないので、落ちたら画面側の変更が原因）
- ブラウザのコンソールにエラーが出ない（`?local=1&cpu=easy&debug=1` で何ターンか遊ぶ）
- スマホの縦画面（幅390px 前後）で、レイアウトが崩れない。PC でも崩れない
- 新しい絵を入れたカード・演出は、実際に出して見る（`debug=1` の手札で、新しいカードを出す）
- 何試合か通して遊び、「待ち時間が長くないか」「出せないカードの理由が分かるか」を PR に書く

### 8. 進め方

- 最初に、現状を見て「直したいこと」を優先順位つきの一覧にして、人間に見せる。**一覧が承認されてから**作業に入る
- 1つの PR は1つの機能にする（例：カードの絵、タイトル画面、勝敗の演出）。大きくなりすぎたら分ける
- コミットメッセージは日本語でよい。何を変えたかが一行で分かるように書く
- 仕様に書かれていないことを決めるとき、仕様と違うやり方にしたいときは、実装する前に必ず人間に確認する
- PR は相手の承認を受けてからマージする。自分で自分の PR をマージしない
